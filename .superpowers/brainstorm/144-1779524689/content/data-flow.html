System Data Flow

End-to-end journeys through the system

① Session Creation → Bot Publishes
1
AdminCreates session in dashboard (date, venue, courts, pub fee)
2
SystemAuto-adds all is_internal=true players to roster as verified_paid
3
AdminSets status → Published
4
FastAPITriggers bot to post formatted message to LOWKEY group + summary to admin group
5
SystemStores telegram_message_id on session record
② Player Joins via Telegram
1
PlayerTaps [Join] inline button in LOWKEY group message
2
BotChecks if telegram_id already registered in players table
↳ Known player → use stored name, skip to step 5
3
BotDMs player: "Hi! What's your name for the roster?"
4
PlayerReplies with name → Bot creates player record
5
SystemChecks if session is full (count active roster ≥ max_pax)
↳ Full → added as waitlisted, bot notifies player
6
SystemInserts roster_entry → Bot edits LOWKEY message with updated list
③ Payment Verification
1
PlayerTransfers via PayNow, sends receipt screenshot to admin directly
2
AdminOpens dashboard → Session → Roster, finds player
3
AdminClicks "Verify Payment" — status → verified_paid
4
BotEdits LOWKEY message: appends "(paid)" next to player name
④ Post-Game P&L
1
AdminSets session status → Completed
2
AdminEnters shuttles used per active batch (can split across batches)
3
SystemUpdates shuttle_batches.remaining_count (auto-deduct)
4
SystemCalculates P&L:
income = sum(verified_paid pub_fee entries)
costs = court_cost + (shuttles × cost_per_shuttle)
net = income − costs
⑤ Admin Removes Player → Waitlist Promotion
1
AdminClicks "Remove" on a roster entry in dashboard
2
SystemDeletes entry, re-numbers positions
3
SystemIf waitlist exists → promotes first waitlisted player to active roster
4
BotNotifies promoted player via DM: "Good news! A spot opened up for [date]."
5
BotEdits LOWKEY message with updated roster
