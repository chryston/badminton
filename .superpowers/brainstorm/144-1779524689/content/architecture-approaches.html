Architecture Approaches

Three ways to deploy the stack — pick your preference

A

All-in-One on Render Recommended

FastAPI + Telegram bot run together as a single persistent service on Render's free tier. Bot uses long polling, keeping the service alive 24/7.

Browser/Mobile → HTTPS → Render: FastAPI ↔ Supabase DB
Render: TG Bot ← long-poll ← Telegram API
Render: TG Bot → edit msg → Telegram API

Pros

  • One service to deploy & monitor
  • Bot long-polling keeps service warm (no cold starts)
  • Simplest mental model
  • Direct function calls between API and bot

Cons

  • Render free tier: 512MB RAM (sufficient)
  • Single point of failure
B

Split: Vercel API + Render Bot

FastAPI runs as serverless functions on Vercel. Bot runs as a separate long-polling worker on Render. They communicate via Supabase Realtime.

Browser/Mobile → Vercel: FastAPI ↔ Supabase
Supabase Realtime → event → Render: Bot Worker
Render: Bot Worker → edit msg → Telegram API

Pros

  • Vercel API: fast, globally distributed
  • Bot logic isolated and independently deployable

Cons

  • Two services to manage
  • Vercel cold starts (~1-2s) on free tier
  • Supabase Realtime adds complexity
C

Fully Serverless on Vercel

FastAPI + Telegram bot webhook both run as Vercel serverless functions. No persistent server needed. Each Telegram update triggers a short-lived function.

Browser/Mobile → Vercel: FastAPI ↔ Supabase
Telegram API → webhook → Vercel: Bot handler
Vercel: Bot handler → edit msg → Telegram API

Pros

  • Zero always-on infrastructure
  • Single deployment target

Cons

  • Vercel free tier: 10s execution limit (risky for bot flows)
  • Cold starts delay Telegram responses
  • Stateless — conversation context (DM name collection) needs workaround

Why A is recommended: The bot's DM conversation flow (asking users for their name) requires tracking state across multiple messages. Long polling on Render handles this naturally with in-memory state. Option C requires storing conversation state in DB between function invocations — added complexity. Option A is also the easiest to debug locally and deploy.
